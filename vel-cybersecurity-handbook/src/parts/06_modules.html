Part 6 — Teaching Format and Module Catalogue

6.1 The 14-point teaching format

Every training module follows the same structure so learners know what to expect and reviewers know what to check.

#ElementWhat it contains
1DefinitionWhat the topic is, in one or two plain sentences
2Business purposeWhy a client or the company cares
3Threat or risk addressedWhat can go wrong without it
4PrerequisitesEarlier modules, knowledge and access needed
5Tool installationOfficial source, version to record, licence
6Safe configurationIsolation, rate limits, authorisation and legal/operational impact
7Step-by-step procedureNumbered actions with exact commands
8Expected outputWhat correct looks like
9VerificationHow to prove it worked
10Common mistakesWhere beginners go wrong
11DocumentationWhat to record, where to file it
12Practical assignmentA task in an owned/vulnerable environment
13AssessmentQuestions and a practical rubric
14Approval requirementWho must sign before the learner proceeds, and what authority results
Rule for every module

Before any tool is used, the module states its legal and operational impact: what traffic it sends, what it may break, and what authorisation it needs. Learners must be able to explain this before they are allowed to run the tool.

6.2 Sample module M-L2-04: Linux accounts, permissions and SSH hardening

M-L2-04 · Level 2 · Linux and Windows Security · Lab-only (A0)
1. DefinitionLinux controls who can log in, what they can read, write or run through accounts, groups, file permissions and the SSH remote-login service. Hardening means removing unneeded access and tightening defaults.
2. Business purposeServers hold client data and run client applications. Weak accounts or open SSH are the commonest route to unauthorised access, outage and loss of trust.
3. Threat / riskPassword guessing against SSH, shared or stale accounts, over-permissive files, privilege escalation through misconfigured sudo or setuid programmes.
4. PrerequisitesM-L1 modules on operating systems, TCP/IP and ports; legal quiz passed; lab isolation verified.
5. Tool installationBuilt into Ubuntu Server LTS: openssh-server, sudo, ufw. Record OS version (lsb_release -a) and OpenSSH version (ssh -V) in the tool register.
6. Safe configurationLab VM on host-only network only. Snapshot first. Keep a second console session open while changing SSH, so a mistake cannot lock you out.
7. Procedure
  1. Review accounts: getent passwd | awk -F: '$7 !~ /(nologin|false)$/ {print $1,$7}'
  2. Find accounts with empty passwords: sudo awk -F: '($2==""){print $1}' /etc/shadow (expected: no output)
  3. Review sudo rights: sudo -l and getent group sudo
  4. Check file permissions on sensitive files: ls -l /etc/shadow /etc/ssh/sshd_config (shadow should not be world-readable)
  5. List setuid files to understand them (read-only): sudo find / -xdev -perm -4000 -type f -ls 2>/dev/null
  6. Create the SSH hardening drop-in /etc/ssh/sshd_config.d/10-vel-hardening.conf as in Part 9, step H3.
  7. Validate syntax before applying: sudo sshd -t (no output means valid), then sudo systemctl reload ssh
8. Expected outputsudo sshd -T shows permitrootlogin no, passwordauthentication no, maxauthtries 3; key login works; password login is refused.
9. VerificationFrom the analyst VM: ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no labadmin@<lab-ip> must return Permission denied (publickey). Check /var/log/auth.log for the attempt.
10. Common mistakesDisabling password login before a key works; editing the main file when an included file overrides it (first value wins); forgetting sshd -t; closing the only session.
11. DocumentationChange log (what, why, before/after), command output excerpts, rollback steps, tool register entry.
12. Practical assignmentHarden SSH on a fresh lab VM, then restore the snapshot and repeat from your own notes without the guide.
13. AssessmentFive written questions (why disable root login? what is "first value wins"? what does sshd -t do?); practical rubric (Part 5.5).
14. ApprovalMentor signs; module counts toward Gate 30. Authority remains A0.

6.3 Sample module M-L6-02: Nmap: safe, authorised network discovery

M-L6-02 · Level 6 · Security Tools · Lab-only until engagement-authorised (T1/T2)
1. DefinitionNmap is a free network scanner that discovers hosts and reports open ports and services. It sends packets to the target; therefore it is an active tool.
2. Business purposeShows the client what is exposed to a network so unnecessary services can be closed and firewall rules verified.
3. Threat / riskUnknown or forgotten services, misconfigured firewalls, shadow systems.
4. PrerequisitesM-L1 TCP/IP and ports; M-L3 firewalls; policy acknowledgement; for any non-lab target, a signed authorisation and A2 authority (T2).
5. Tool installationOfficial project: nmap.org. Ubuntu: sudo apt install -y nmap. Record version with nmap --version. Licence: Nmap Public Source License (check terms for redistribution).
6. Legal & operational impactScanning someone else's network without permission may be illegal in your jurisdiction. Scans can trigger alarms, fill logs, and occasionally crash fragile devices. Use rate limits and agreed windows.
7. Procedure (lab)
  1. Confirm the target IP is in your Lab Authorisation Record and is a VEL lab VM.
  2. Host discovery on the lab subnet only: nmap -sn 192.168.56.0/24
  3. Top-port scan with service versions: nmap -sV --top-ports 1000 -oA lab01-baseline 192.168.56.101
  4. Compare scans before and after hardening using the saved .nmap files.
  5. For firewalled targets, add --max-retries 1 to avoid long waits.
8. Expected outputBefore hardening: SSH plus any lab services listed as open. After hardening: only the intended ports open; others filtered.
9. VerificationCross-check with ss -tulpn on the target. Anything Nmap reports but the host does not list is investigated (NAT, firewall, container).
10. Common mistakesScanning the whole home or office LAN; typing a wrong subnet; scanning a public IP "to test"; running aggressive scripts without approval; forgetting to save output.
11. DocumentationCommand, version, time, target, output files (hash), person, approval reference.
12. Practical assignmentWrite a one-page "scan plan" for the lab (targets, settings, impact, stop conditions), have it approved, then execute and report.
13. AssessmentExplain the impact of -sn, -sV and --top-ports; identify out-of-scope IPs in a sample list.
14. ApprovalSecurity Lead approval of the scan plan for each non-lab use; Tier follows Part 3.

6.4 Sample module M-L6-05: Secret scanning with Gitleaks

M-L6-05 · Level 6 · Dependency and secret scanning · Lab (Project 5) then Tier 1
1. DefinitionGitleaks searches files and Git history for strings that look like passwords, API keys or tokens.
2. Business purposeLeaked credentials let outsiders sign in as the company. Finding them early lets the client revoke them.
3. Threat / riskHard-coded cloud keys, database passwords and tokens committed to repositories, including old commits.
4. PrerequisitesGit basics; M-L4 authentication concepts; for client repositories: authorisation naming the repositories and a read-only clone.
5. Tool installationOfficial project: github.com/gitleaks/gitleaks (releases or package manager). MIT licence. Record version with gitleaks version.
6. Safe configurationRun on a local read-only clone. Use --redact so reports do not store full secrets. Never paste real secrets in tickets or chat.
7. Procedure
  1. Create a training repo with fake secrets only. For example, AWS's documented example key AKIAIOSFODNN7EXAMPLE in a file, committed, then deleted in a later commit.
  2. Scan including history: gitleaks detect --source . --redact --report-format json --report-path gitleaks-report.json
  3. Newer versions also provide gitleaks git and gitleaks dir; check gitleaks --help for your version.
  4. Review each hit: real secret, example, or false positive? Record the decision.
  5. Recommend: revoke and rotate the credential, remove from code, use a secrets manager, add a pre-commit scan.
8. Expected outputA report listing rule ID, file, commit and line, with the secret value redacted.
9. VerificationDelete the fake key from the current file: the history scan still finds it in the old commit. This shows why rotation matters more than deletion.
10. Common mistakesBelieving deletion fixes a leak; sharing the unredacted report; ignoring false positives without a recorded reason; testing a real secret to "see if it works" (this is unauthorised access).
11. DocumentationFinding record with commit hash, location, status (confirmed/false positive), recommended action; reports kept in restricted store.
12. Practical assignmentScan the training repo, triage ten hits, write a one-page remediation plan including a pre-commit hook configuration.
13. AssessmentWhy can a "deleted" secret still be dangerous? What must never be done with a discovered credential?
14. ApprovalLab: mentor sign-off. Client repos: Security Lead confirms the repository is named in scope (T1).
Never validate a discovered credential

Do not try a found key or password against a live system to see whether it works, unless the RoE explicitly permits that exact check. Report it, recommend revocation, and let the owner decide.

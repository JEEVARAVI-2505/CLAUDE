Authority requiredA0 (trainee) with a signed Lab Authorisation Record

Lab rule

Every IP address you scan, probe or log in to in this lab must be one of your own lab VMs, listed in your Lab Authorisation Record. If a command could reach any other address, stop and ask.

9.1 Objectives and learning outcomes

  • Build an isolated lab and prove that it is isolated.
  • Capture a baseline of a default Linux server and identify its weaknesses.
  • Apply ten hardening controls safely, with backups, verification and rollback.
  • Compare before and after results and write an evidence-based hardening report.
  • Practise the habit: authorise, snapshot, change, verify, document.

9.4 Phase A: Authorise and isolate (Day 1)

  1. Sign the Lab Authorisation Record (Appendix C) listing VM names, IPs, purpose and dates. The Security Lead countersigns.
  2. Create the host-only network in your hypervisor. Do not choose "bridged" for any lab VM.
  3. Install lab01-target and lab01-analyst. Create an admin user labadmin (not root); install OpenSSH server when asked.
  4. Update the target while the temporary NAT adapter is attached: 
    sudo apt update && sudo apt full-upgrade -y
sudo reboot
  5. Remove the NAT adapter from lab01-target (VM powered off, then in the hypervisor network settings). Boot the VM.
  6. Prove isolation on lab01-target: 
    ip -br addr                 # only the host-only address (e.g. 192.168.56.101)
ip route                    # no default route
ping -c 2 -W 2 1.1.1.1      # must FAIL (network unreachable / 100% loss)
ping -c 2 192.168.56.10     # must succeed (analyst VM)
  7. Take snapshot "S0-clean-isolated" of both VMs.
Isolation check passed only if the target cannot reach the Internet and no lab VM is bridged to your LAN.

9.5 Phase B: Baseline (Day 2)

Record the "before" state. Save outputs to lab01/evidence/baseline/ on your workstation (no real data; safe to store in the training repo).

  1. Configuration backup on the target: 
    sudo tar czf /var/backups/etc-baseline-$(date +%F).tgz /etc
sha256sum /var/backups/etc-baseline-*.tgz | tee ~/etc-baseline.sha256
  2. System facts: 
    lsb_release -a; uname -r; ssh -V
getent passwd | awk -F: '$7 !~ /(nologin|false)$/ {print $1,$7}'
sudo awk -F: '($2==""){print $1}' /etc/shadow
sudo ss -tulpn
systemctl list-unit-files --type=service --state=enabled
sudo sshd -T | grep -Ei '^(permitrootlogin|passwordauthentication|maxauthtries|x11forwarding|logingracetime)'
sudo ufw status verbose
  3. External view from lab01-analyst (own lab IP only): 
    nmap -sV --top-ports 1000 -oA ~/lab01-baseline 192.168.56.101
  4. Optional audit score. On the target: 
    sudo apt install -y lynis    # temporary NAT needed, or use an offline package
sudo lynis audit system
    Note the "Hardening index" and warnings. The audit is read-only.
  5. Write down weaknesses you see (for example: password login enabled, no firewall, unnecessary services) as draft findings with a likelihood and impact rating (Part 7.4).
  6. Snapshot "S1-baseline".

If the target has no internet, install packages needed for later steps (ufw fail2ban auditd libpam-pwquality unattended-upgrades lynis) before removing the NAT adapter, or reattach NAT briefly; remove it again and re-run the isolation check.

9.6 Phase C: Hardening controls H1–H10 (Days 2–4)

Safety rules for every step
  • Keep a second console session (hypervisor console) open when you change SSH or the firewall.
  • Change one control at a time, verify, then record in the change log.
  • If anything breaks, revert the snapshot or the specific file, and note why.

H1 · Patching and automatic security updates

sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades      # choose Yes
sudo unattended-upgrade --dry-run --debug | tail -n 5

Why: known vulnerabilities are the easiest way in. Verify: systemctl is-enabled unattended-upgrades returns enabled; the dry run completes without errors. Rollback: sudo apt remove unattended-upgrades.

H2 · Accounts and password quality

sudo passwd -l root                                   # lock the root password (sudo still works)
sudo apt install -y libpam-pwquality
sudo sed -i 's/^# *minlen.*/minlen = 14/' /etc/security/pwquality.conf
grep -E '^minlen' /etc/security/pwquality.conf
sudo awk -F: '($2==""){print $1}' /etc/shadow         # expect no output

Why: limits shared or guessable credentials. Verify: sudo passwd -S root shows L (locked); no accounts with empty passwords. Decision log: list each remaining login-capable account with owner and purpose; remove or lock any without one.

H3 · SSH: key login only, no root, limited attempts

On lab01-analyst create a key and copy it:

ssh-keygen -t ed25519 -C "lab01-analyst"
ssh-copy-id labadmin@192.168.56.101
ssh labadmin@192.168.56.101        # must log in with the key

On lab01-target create the drop-in file (it must sort before cloud-init files, because the first value wins):

sudo tee /etc/ssh/sshd_config.d/10-vel-hardening.conf >/dev/null <<'EOF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
LoginGraceTime 30
X11Forwarding no
AllowUsers labadmin
EOF
sudo sshd -t && sudo systemctl reload ssh

Verify (from analyst): ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no labadmin@192.168.56.101 must give Permission denied (publickey). On target: sudo sshd -T | grep -Ei '^(permitrootlogin|passwordauthentication|maxauthtries|allowusers)'. Rollback: sudo rm /etc/ssh/sshd_config.d/10-vel-hardening.conf && sudo systemctl reload ssh (use the hypervisor console if SSH is locked).

H4 · Host firewall (UFW), default deny

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.56.0/24 to any port 22 proto tcp
sudo ufw logging on
sudo ufw enable
sudo ufw status verbose

Always add the SSH allow rule before enabling. Verify: status shows Status: active, default deny (incoming), and port 22 allowed from the lab subnet. Rollback: sudo ufw disable.

H5 · Reduce attack surface

sudo ss -tulpn                                         # what listens?
systemctl list-unit-files --type=service --state=enabled
# Only after confirming a service is unneeded and recording the decision:
sudo systemctl disable --now <service-name>

Why: every listening service is a possible weakness. Verify: only SSH (port 22) listens on the lab address, apart from local-only services such as the system resolver on 127.0.0.53. Never disable a service you cannot explain.

H6 · Brute-force protection (fail2ban)

sudo apt install -y fail2ban
sudo tee /etc/fail2ban/jail.d/vel-sshd.local >/dev/null <<'EOF'
[sshd]
enabled  = true
backend  = systemd
maxretry = 4
findtime = 10m
bantime  = 1h
EOF
sudo systemctl enable --now fail2ban
sudo systemctl restart fail2ban
sudo fail2ban-client status sshd

Verify: the jail sshd is listed and active. Optional, own lab only: from the analyst VM, try logging in as a non-existent user a few times (ssh nosuchuser@192.168.56.101); check sudo fail2ban-client status sshd for a banned address, then unban with sudo fail2ban-client set sshd unbanip 192.168.56.10.

H7 · Audit logging (auditd)

sudo apt install -y auditd
sudo tee /etc/audit/rules.d/vel-lab01.rules >/dev/null <<'EOF'
-w /etc/passwd -p wa -k identity
-w /etc/shadow -p wa -k identity
-w /etc/sudoers -p wa -k sudoers
-w /etc/sudoers.d/ -p wa -k sudoers
-w /etc/ssh/sshd_config -p wa -k sshd
-w /etc/ssh/sshd_config.d/ -p wa -k sshd
EOF
sudo augenrules --load
sudo auditctl -l

Verify: create and remove a harmless file sudo touch /etc/ssh/sshd_config.d/zz-test.conf; sudo rm /etc/ssh/sshd_config.d/zz-test.conf, then sudo ausearch -k sshd -ts recent shows the events. Why: you cannot investigate what you did not log.

H8 · Time synchronisation and kernel network settings

timedatectl                                            # System clock synchronized: yes
sudo tee /etc/sysctl.d/90-vel-lab01.conf >/dev/null <<'EOF'
net.ipv4.conf.all.rp_filter = 1
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.all.send_redirects = 0
net.ipv6.conf.all.accept_redirects = 0
net.ipv4.tcp_syncookies = 1
net.ipv4.conf.all.log_martians = 1
kernel.randomize_va_space = 2
EOF
sudo sysctl --system | tail -n 5

Verify: sysctl net.ipv4.tcp_syncookies kernel.randomize_va_space returns the values set. Note: accurate time makes logs trustworthy. Without the NAT adapter, time sync may need the hypervisor's guest tools or a lab NTP source; record what you used.

H9 · File permissions and privileged programmes

ls -l /etc/shadow /etc/passwd /etc/ssh/sshd_config
sudo find / -xdev -type f -perm -0002 -ls 2>/dev/null       # world-writable files
sudo find / -xdev -perm -4000 -type f -ls 2>/dev/null      # setuid programmes (review only)
chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys

Verify: no unexpected world-writable files; each setuid programme is a normal system component you can explain. Do not remove setuid bits you do not understand; note them as questions for your mentor.

H10 · Backup and configuration baseline

sudo tar czf /var/backups/etc-hardened-$(date +%F).tgz /etc
sudo sha256sum /var/backups/etc-hardened-*.tgz | tee ~/etc-hardened.sha256

Verify: extract both archives into separate folders and run diff -ru baseline/etc hardened/etc; every difference corresponds to a change-log entry. Take snapshot "S2-hardened". Proof of rollback: restore S1-baseline, confirm the weak settings are back, then restore S2.

9.8 Common mistakes and troubleshooting




SymptomLikely cause / fix



Cannot SSH after H3Key not copied or AllowUsers wrong. Use the hypervisor console, remove the drop-in, reload, repeat step by step.


sshd -T still shows passwordauthentication yesAnother file set it first. List /etc/ssh/sshd_config.d/; your file must sort earlier (e.g. 10-).


Locked out after enabling UFWSSH allow rule missing or wrong subnet. Console: sudo ufw allow from 192.168.56.0/24 to any port 22 proto tcp.


Nmap scan is very slow after the firewallDropped packets cause retries. Use --top-ports 1000 --max-retries 1.


Packages fail to installNo network (NAT removed). Install needed packages first, or briefly re-attach NAT and re-check isolation.


fail2ban shows no jailCheck /etc/fail2ban/jail.d/vel-sshd.local spelling and sudo journalctl -u fail2ban -n 30.


Scanned an IP not in your recordStop. Report to the Security Lead immediately (Part 3.11).

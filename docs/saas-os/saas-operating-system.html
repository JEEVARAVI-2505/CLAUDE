Critical rules (non-negotiable)

  1. Never start coding before product scope approval (G2).
  2. Never launch without testing and security review.
  3. Never estimate production cost without documenting usage assumptions.
  4. Never confuse one-time development cost with monthly operating cost.
  5. Never treat free-tier services as guaranteed permanent infrastructure.
  6. Never invent domain availability or DNS values.
  7. Never calculate profit using revenue alone.
  8. Never hide recurring third-party costs.
  9. Never ignore maintenance and customer-support labour.
  10. Never recommend an expensive architecture without justification.
  11. Never claim a product is production-ready without evidence.
  12. Never proceed past an approval gate without authorisation.

Reading a stage

Every stage card has the same ten parts: instructions, responsibilities, tools, time, cost, deliverables, quality checklist, approval criteria, official sources, common mistakes. Stage 1–11 follow product order; 12–14 are continuous disciplines.

1Market Research & Opportunity G1 – Opportunity Approval

Prevents building a product nobody will pay for. No code is written until the owner signs G1.

1. Detailed instructions

  1. Define target market and customer segment; write the problem statement in one sentence (who, what pain, how they cope today).
  2. Interview at least 10 target customers (Customer Discovery template). Record willingness to pay as a stated price range, not a yes/no.
  3. List 5–10 competitors (direct and indirect). For each: pricing page, feature list, tech stack signals, positioning, reviews (G2, Capterra, Product Hunt, Reddit). Record URL and access date.
  4. Build the feature/pricing comparison matrix; extract gaps and the differentiator.
  5. Define Ideal Customer Profile (ICP); name buyer, end user and decision-maker (often three different people).
  6. Estimate sales cycle and acquisition difficulty (channel, effort, expected CAC range).
  7. Size the market bottom-up: TAM = all potential customers × annual contract value; SAM = reachable segment (geography, size, language); SOM = share winnable in 3 years given capacity. Show every assumption.
  8. Identify recurring-revenue levers: subscription tiers, usage add-ons, onboarding fee, support plans.
  9. Write the Market Research and Product Opportunity Report; submit for G1.

2. Employee responsibilities

RoleResponsibility
Product OwnerOwns report and the go/no-go recommendation
Researcher / AnalystCollects sources, builds comparison matrix
Business OwnerApproves or rejects at G1

3. Required tools

Google Sheets/Excel, G2, Capterra, Product Hunt, Reddit, Google Trends, competitor sites, government/industry reports, interview recording (with consent).

4. Estimated time

2–3 weeks (about 41 h expected for the sample product)

5. Estimated cost

Labour only: ≈ ₹50,000 expected (41 h × ₹1,200). No tooling cost required.

6. Expected deliverables

  • Market Research & Product Opportunity Report
  • Competitor Analysis sheet (with URLs + access dates)
  • Customer Discovery notes (≥10)
  • TAM/SAM/SOM workbook

7. Quality checklist

  • ☐ ≥5 competitors compared with source links
  • ☐ Every number has a source or is tagged ASSUMPTION
  • ☐ ≥10 customer conversations logged
  • ☐ ICP, buyer, user, decision-maker named
  • ☐ TAM/SAM/SOM bottom-up with arithmetic shown
  • ☐ Recurring revenue path identified
  • ☐ Risks and kill criteria written

8. Approval criteria

Business Owner signs G1 in the dashboard. Kill criteria: <3 of 10 prospects confirm the pain as top-3 priority, or stated willingness to pay below projected break-even price.

9. Official source references (verify and record access date)

  • Google Trends https://trends.google.com/

2Product Requirements & Scope Freeze G2 – Scope Freeze

Defines exactly what will be built; later change is controlled and priced.

1. Detailed instructions

  1. Write the PRD: purpose, customers, user roles and permission matrix, core modules, features/sub-features, user journeys.
  2. Write the Input–Output Specification: for every input (name, type, unit, required, default, validation, min/max, source, DB mapping) and every output (name, format, calculation, precision, display, export, API shape, error handling).
  3. Add non-functional requirements: security, performance targets, mobile responsiveness, browser matrix, backup RPO/RTO, maintenance windows.
  4. Write acceptance criteria in Given/When/Then form for every feature; attach at least one sample input→output scenario.
  5. Review with customer(s) and engineering; resolve open questions.
  6. Freeze: record version, date and approvers. All later changes go through a Change Request.

2. Employee responsibilities

RoleResponsibility
Product OwnerAuthors PRD, owns acceptance criteria
Tech LeadReviews feasibility, estimates, NFRs
QA LeadConfirms every criterion is testable
Customer / Business OwnerApproves scope

3. Required tools

Docs/Notion/Confluence, Figma (journey maps), spreadsheet for I/O spec, dashboard approval module.

4. Estimated time

2–3 weeks (≈ 78 h)

5. Estimated cost

Labour: ≈ ₹98,500 expected (Product Owner + Tech Lead hours).

6. Expected deliverables

  • Approved PRD
  • Input–Output Specification
  • Scope Freeze Document (versioned)
  • Change Request log (empty at freeze)

7. Quality checklist

  • ☐ All 20 PRD headings present
  • ☐ Every input and output specified
  • ☐ Every feature has acceptance criteria
  • ☐ Out-of-scope list explicit
  • ☐ Permissions matrix complete
  • ☐ NFR numbers measurable (e.g. p95 < 500 ms)
  • ☐ Signed by customer and product owner

8. Approval criteria

G2 signed by Product Owner and Customer. A Change Request needs: ID, business justification, technical, cost, timeline and security impact, customer approval and product-owner approval.

3Technology Stack & Architecture G3 – Architecture Approval

Chooses the cheapest architecture that safely meets the requirements, with documented trade-offs.

1. Detailed instructions

  1. Draft at least two architecture options (e.g. A: Next.js + Node/TypeScript + PostgreSQL modular monolith on a managed PaaS; B: React SPA + FastAPI + PostgreSQL on a single cloud VM/containers).
  2. Score each option 1–5 on: development cost, hosting cost, maintenance cost, scalability, security, performance, developer availability, vendor lock-in, integration fit, long-term operating cost. Weight by project priorities.
  3. Default to a modular monolith for the MVP. Microservices require a written justification (independent scaling, team boundaries, compliance isolation).
  4. Produce: system diagram, frontend, backend, database architecture, ERD, API documentation (OpenAPI), authentication architecture, threat model (STRIDE), infrastructure diagram, technology justification.
  5. Run the threat model against OWASP Top 10 and ASVS level 1 (level 2 for payments/personal data).
  6. Tech Lead presents; Business Owner approves cost implications.

Product OwnerConfirms fit to requirements

1–2 weeks

5. Estimated cost

Labour ≈ ₹92,500 (Tech Lead database/API design hours in sample).

6. Expected deliverables

  • OpenAPI draft

  • Infrastructure diagram
  • Decision log (ADR)

7. Quality checklist

  • ☐ Auth, session and RBAC design written
  • ☐ Secrets management defined
  • ☐ Backups and RPO/RTO defined
  • ☐ Cost of each option estimated

5VS Code, GitHub & Project Initialisation G5 – Repo Readiness

Every project starts from the same secure, automated baseline.

1. Detailed instructions

  1. Install standard tools: VS Code (with approved extensions), Git, approved Node/Python runtime and package manager, API client, DB client, browser dev tools, test runners.
  2. Create a PRIVATE GitHub repository under the company organisation; add description and README.
  3. Create the standard structure (apps/web, apps/api, packages/ui, packages/shared, docs/*, tests/{unit,integration,e2e}, infra, .github/{workflows,ISSUE_TEMPLATE}, .env.example, .gitignore, README.md, CONTRIBUTING.md).
  4. Protect main: require PR, ≥1 approving review, passing status checks, no force-push, linear history.
  5. Branches: feature/-, fix/-, hotfix/-. Commits: Conventional Commits (feat:, fix:, docs:, chore:).
  6. CI: lint, type-check, unit tests, build, dependency audit, secret scanning, CodeQL/static analysis. Enable Dependabot.
  7. Create three environments (local, staging/preview, production) with separate databases and secrets.
  8. Tag releases with semantic versions and publish release notes.

7Production Cost Calculation (mandatory) G7 – Cost Model Approval

Prevents under-pricing by costing development, launch AND operation. Never quote from domain + hosting alone.

1. Detailed instructions

  1. Labour: hours × fully loaded hourly cost per role, three scenarios (optimistic, expected via PERT = (O + 4M + P) / 6, pessimistic). Include founder time.
  2. One-time infrastructure/setup: domain, DNS, hosting, DB, email, SSL, storage, monitoring, payment gateway, backups, pipeline, legal, integrations. Mark each mandatory or optional.
  3. Monthly cost: domain, hosting, database, storage, CDN, email, SMS/WhatsApp, auth, APIs, AI, monitoring, backups, security, payment fees, maintenance, support, misc.
  4. Pull every unit price from the provider's current official pricing page; store URL + access date. If unavailable mark ASSUMPTION. Never invent a price.
  5. Capacity: model 10, 50, 100, 500, 1,000, 5,000, 10,000 users via MAU, DAU, peak concurrency, requests, queries, storage, bandwidth, emails, background jobs. Use low/medium/high scenarios if no data. Find the real bottleneck; do not multiply linearly.
  6. Cost three architectures: Lean MVP, Professional, Scalable. Report setup, monthly infra, maintenance, annual, capacity, limits, risks, upgrade triggers.
  7. Apply the formulas in section 'Financial Model' and allocate shared costs once (usage, reserved capacity or time share).

8SaaS Pricing & Profitability G8 – Pricing Approval

Sets a price that covers full cost, CAC and churn with a target margin.

1. Detailed instructions

  1. Cost-based: (cost to serve + fixed share + target margin). Competitor-based: positioning within the observed range. Value-based: share of customer's quantified saving. Choose the price inside the intersection.
  2. Compute CAC, MRR, ARR, gross margin (state which costs sit in cost of revenue), contribution margin, break-even customers, operating profit; show tax separately.
  3. Define plans: Free Trial (if suitable), Starter, Professional, Business, Enterprise — price (monthly/annual), users, storage, API limits, features, support, overage, upgrade rule.
  4. Include payment-gateway fees, refunds, discounts, GST, failed payments, churn.
  5. Never promise 'unlimited' without a cost and abuse-control rule (fair-use limit, rate limiting).
  6. Recommend setup fee, subscription fees, minimum viable price, target gross margin, maximum CAC, break-even customers, monthly revenue target, renewal strategy.

9Domain, DNS & Production Deployment G9 – Release Approval

Takes the product from repository to a safe, monitored, rollback-able live service.

1. Detailed instructions

  2. DNS: copy exact records supplied by the hosting and email providers (A/AAAA/CNAME/MX/TXT/SPF/DKIM/DMARC/CAA). Keep existing email records. Never guess a value.
  3. Deploy: connect repo → build settings → production env vars → production DB → storage → domain → DNS → verify propagation → TLS → HTTPS redirect → migrations → backups → monitoring → error tracking → alerts → smoke tests → critical workflow tests → rollback test → release approval.
  4. Record every value in the Domain/DNS Report and Deployment Report.

S8. Customer delivery

  1. Pilot with 3 clinics for 60 days at 50% price; written consent for case study.
  2. SOW covering: configuration, data import, training (2 × 90 min), acceptance tests.
  3. Subscription terms: monthly/annual billing, fair-use limits, data export on exit within 30 days, data deletion within 90 days, customer owns its data; company owns platform code and reusable components; third-party licences remain with licensors.
  4. Handover pack: user manual, admin manual, support contacts and hours, escalation matrix.

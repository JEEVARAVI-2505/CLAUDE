PART 1

How a software company works

1.1 What a software company really is

A software company turns a customer's problem into a working product and then keeps it working while customers pay for it. Everything in this handbook exists to make that repeatable: the same steps, in the same order, with the same checks, whoever does the work. Corporate work is not about being clever alone; it is about being predictable, documented and reviewed.

1.5 How work flows: from request to done

  1. Work starts as a ticket (an item on the board) written by the PO: what, why, acceptance criteria.
  2. Board columns: Backlog → To Do → In Progress → In Review → In Test → Done. Only move a ticket when the exit rule of its column is true.
  3. A ticket in In Progress has your name, a branch, and an estimate in hours. Nobody works on something without a ticket.
  4. A ticket reaches Done only when it meets the Definition of Done (section 3).
  5. New ideas during work are not built. They become a new ticket or a Change Request for the PO to decide.

1.8 Professional communication

  • Write so someone can act without asking you again: context, what you did, what you need, by when.
  • Ask for help after 30 minutes of honest effort. Bring: what you wanted, what you tried, the exact error text, a screenshot.
  • Bad news early is a small problem; bad news late is a big one. Say 'I am blocked' or 'this will take longer' as soon as you know.
  • Be polite and specific in code reviews. Review the code, never the person.
  • Answer messages within the same working day; acknowledge long ones with 'seen, will reply by 4 pm'.

1.9 Confidentiality and conduct

  • Customer data, source code, prices, contracts and plans are confidential. Do not share them outside the company.
  • Use only company-approved tools and accounts for company work. Do not use personal email or personal cloud storage.
  • Do not install pirated software; use only licences the company owns or free, permissively licensed software approved by the Tech Lead.
  • Report any suspected security problem immediately to the Tech Lead, even if it was your mistake. Hiding it is the real offence.

Ground rules, Definition of Done, asking for help

3.1 The ten rules

#RuleWhat it means for you
1Never work without a ticket.If it is not on the board, it is not approved work.
2Never commit passwords, keys or customer data.Use environment variables. If you commit one by accident, tell the Tech Lead at once; the secret must be replaced, not just deleted.
3Never push straight to main.Always branch → Pull Request → review → merge.

9Never claim 'done' without proof.Done = passes acceptance criteria + tested + reviewed + documented + demonstrated.

How to Use This Playbook

This document is the single operating manual for the Cloud Engineering & DevOps division. It does two jobs: (1) it trains a beginner from zero to a professional who can join supervised client projects, and (2) it defines the mandatory lifecycle every client project follows, with approval gates, deliverables and acceptance criteria.

Golden rules
  1. Do not skip stages. Do not start a stage until the previous stage's acceptance criteria are met and its approval gate is signed.
  2. “It runs” is not “it is production-ready.” Production-ready means secure, monitored, backed up, restorable, documented, cost-controlled and handed over.
  3. Never run destructive commands (rm -rf, terraform destroy, database drops) without understanding the effect and having a verified backup.
  4. Never put passwords, keys or tokens in Git, chat, documents or the company portal.
  5. Never promise savings, uptime or security outcomes without evidence.
  6. Every production change needs a second person's review.

Core exercises

  1. Create user deploy, add to group www-data, prove its permissions with id.
  2. Install Nginx: sudo apt update && sudo apt install -y nginx; confirm systemctl status nginx and curl localhost.
  3. Enable the firewall after allowing SSH, so you do not lock yourself out: 
    sudo ufw allow OpenSSH
sudo ufw allow 80,443/tcp
sudo ufw enable
sudo ufw status verbose
  4. Write a cron job that records disk usage daily: 0 2 * * * /usr/local/bin/disk-report.sh.
  5. Harden SSH: key-only login, no root login (PasswordAuthentication no, PermitRootLogin no). Test a second session before closing the first.

Hardening baseline (checklist)

  • Individual accounts + sudo; no shared logins
  • SSH keys, MFA on cloud console, fail2ban or equivalent
  • Unattended security updates; patch schedule
  • Firewall default-deny inbound
  • Time sync, log retention, disk-space alerts

Common mistakes: enabling firewall before allowing SSH; editing sshd_config without a backup and second session; running everything as root.
Assessment: practical — provision a clean Ubuntu VM, harden it and host a static page in 60 minutes unaided.

Practical exercises

  1. Build a small local network (two VMs, one subnet) and ping between them.
  2. Trace DNS: dig +trace example.com; explain each hop.
  3. Connect to a remote Linux server by SSH key.
  4. Configure a firewall that allows only 22 (your IP), 80, 443.
  5. Diagnose a failed connection with this ladder: ping (reachable?) → dig (name resolves?) → nc -vz host 443 (port open?) → firewall / security group → service listening (ss -tulpn) → app logs.
  6. Serve a test app over HTTPS with Nginx and a certificate; verify with curl -vI https://host.

Common mistakes: overlapping CIDR ranges that block later VPC peering; forgetting DNS TTL delays; putting a database in a public subnet.

#!/usr/bin/env bash
# backup.sh - dated archive with 7-day retention. Test on a copy first.
set -euo pipefail
SRC="/var/www/app"; DEST="/backups"; STAMP=$(date +%F)
mkdir -p "$DEST"
tar -czf "$DEST/app-$STAMP.tar.gz" "$SRC"
find "$DEST" -name 'app-*.tar.gz' -mtime +7 -print -delete
echo "backup ok: $DEST/app-$STAMP.tar.gz"

Common mistakes: hard-coding secrets; ignoring exit codes; unquoted variables in rm/find -delete; no logging.

Client Project Lifecycle: Stages 01–18

Every client project follows these 18 stages in order. Each stage lists its objective, steps, deliverables, acceptance criteria and approval gate. A stage is closed only when the gate is signed by the named approver.

01 Lead→02 Discovery→03 Scope/SOW→04 Architecture→05 Cost→06 Dev env→07 Repo→08 IaC→09 Docker→10 CI/CD→11 K8s*→12 Security→13 Monitoring→14 Backup/DR→15 QA→16 Production→17 Handover→18 Managed service

*Stage 11 only when Kubernetes is justified (see toolchain section).

Stage 01 — Lead Qualification

Objective: decide whether this client is a good fit before spending engineering time.

Collect: company name; industry; size; current application/infrastructure; business problem; expected outcome; technical requirements; estimated users and traffic; current hosting; budget range; timeline; security/compliance needs; decision-maker.

Deliverables: lead qualification document; discovery notes; opportunity assessment (fit score, risks, red flags such as “wants guaranteed 100% uptime on a tiny budget”).

Gate 1Sales/Project Manager approves proceeding. Acceptance: all fields above filled or marked “unknown” with an owner.

Stage 02 — Client Discovery and Technical Assessment

Objective: understand reality before designing anything. Run a structured meeting; never assume.

AreaQuestions to ask
InfrastructureWhat runs where? Servers, versions, regions, who has access, any diagrams?
ApplicationLanguages, frameworks, databases, third-party integrations, build and deploy steps today.
Traffic & availabilityUsers today / in 12 months, peak times, tolerated downtime per month.
DataSensitivity (personal, financial, health), location constraints, retention, encryption today.
Backup & recoveryWhat exists? Has restoration ever been tested? Acceptable data loss (RPO) and downtime (RTO)?
CostCurrent monthly cloud spend, invoices, known waste.
LimitsLegacy dependencies, licences, skills in the client team, policy restrictions.

Deliverables: discovery questionnaire (completed); current-state architecture diagram; infrastructure inventory; risk and dependency register.

Gate 2Client confirms in writing the problem statement and requirements. Acceptance: inventory matches what the client can verify.

Stage 03 — Requirements and Scope Freeze (SOW)

Create a formal Statement of Work containing: objectives; in-scope and out-of-scope services; technical and infrastructure requirements; deliverables; responsibilities (ours vs client); timeline and milestones; dependencies; acceptance criteria; support period; change-request procedure.

Do not start implementation without (1) approved scope, (2) agreed commercial terms, (3) written access authorisation. Access is granted to named individuals with individual accounts, never shared admin credentials.

Change-request procedure

  1. Client or team raises the change in writing.
  2. Project Manager assesses impact on cost, time and risk.
  3. Client approves the revised quote/timeline.
  4. SOW addendum is signed before work begins.

Stage 04 — Infrastructure Architecture Design

Design ten views: application, cloud, network, database, storage, security, deployment, backup, monitoring, disaster recovery.

Create: system architecture diagram; network topology; component list; data-flow diagram; security-boundary diagram; deployment-flow diagram; Architecture Decision Records (ADRs).

Compare at least two options

Gate 4Technical Lead and client approve the architecture.

Stage 05 — Cloud Cost Estimation and Commercial Approval

Estimate before provisioning. Never invent prices; use the provider's official calculator and record region, currency, pricing date, usage assumptions and taxes. Estimates are not guaranteed bills.

GroupItems
A. One-timeDiscovery, architecture, infrastructure setup, networking, migration, CI/CD, testing, documentation, training
B. RecurringVMs, containers, Kubernetes, storage, databases, backups, bandwidth/data transfer, load balancers, DNS/certificates, monitoring, security tools, logging, support, third-party subscriptions
C. InternalDeveloper hours, tech-lead review, project management, QA, support, contingency
Total Monthly Cloud Cost = Compute + Storage + Database + Network + Backup
                         + Monitoring + Security + Other services
Total Project Cost       = Labour + Setup + Migration + Testing + Tools + Other direct costs
Selling Price            = Total Delivery Cost + Risk Allowance + Target Profit

Also calculate gross margin, contribution margin, break-even, MRR, ARR, expected cloud cost per customer, cost per active user. Provide scenarios at 100, 1,000, 10,000 and 100,000 users where relevant (see worked template in the pricing section).

Gate 5Project Manager and an authorised commercial representative approve the estimate.

Adapt to the project; do not create empty folders for appearance. Explain every folder to the trainee.

Never commitpasswords, private keys, API secrets, cloud credentials, production env files, customer personal data, database dumps with sensitive data. Add them to .gitignore and scan with Gitleaks. If a secret is committed: revoke and rotate it immediately.

Repository rules: protected main branch; pull requests with at least one review; meaningful commit messages (feat:, fix:, docs:); release tags such as v1.2.0.

Stage 08 — Infrastructure as Code

What: describe infrastructure in text files so it is repeatable, reviewable and versioned. Process (follow in order):

  1. Install Terraform or OpenTofu.
  2. Authenticate securely (SSO / short-lived credentials).
  3. Provider configuration.
  4. Variables, 5. outputs, 6. reusable modules.
  5. Remote state with locking (e.g. S3 + DynamoDB lock or native locking where supported).
  6. fmt + validate.
  7. Review the plan; 9. obtain approval; 10. apply; 11. verify resources; 12. document; 13. test controlled destroy in non-production.
provider "aws" { region = var.region }

variable "region"      { type = string  default = "ap-south-1" }
variable "environment" { type = string }

resource "aws_s3_bucket" "assets" {
  bucket = "client-${var.environment}-assets"
}
resource "aws_s3_bucket_public_access_block" "assets" {
  bucket                  = aws_s3_bucket.assets.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
output "assets_bucket" { value = aws_s3_bucket.assets.bucket }
Production ruleNo production apply without peer review of the plan, a relevant backup, and explicit approval. Read every line marked destroy or replace.

Stage 09 — Docker and Containerisation

Concepts: container vs VM; image vs container; Dockerfile; Compose; volumes; networks; env vars; registries; multi-stage builds; image size; health checks; non-root users; image scanning.

# Dockerfile: multi-stage, non-root, health check
FROM python:3.12-slim AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim
RUN useradd -r -u 10001 appuser
WORKDIR /app
COPY --from=build /install /usr/local
COPY src/ ./src/
USER appuser
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s CMD python -c "import urllib.request;urllib.request.urlopen('http://localhost:8080/health')"
CMD ["python","-m","src.main"]
# docker-compose.yml (development)
services:
  app:
    build: ./application
    ports: ["8080:8080"]
    environment:
      DATABASE_URL: ${DATABASE_URL}      # from untracked .env
    depends_on: [db]
    deploy: { resources: { limits: { cpus: "0.5", memory: 256M } } }
  db:
    image: postgres:16
    environment: { POSTGRES_PASSWORD: ${DB_PASSWORD} }
    volumes: [dbdata:/var/lib/postgresql/data]
volumes: { dbdata: {} }

Test: startup; /health; DB connection; docker restart (app recovers); data survives container removal (volume); failure handling (stop DB, app logs a clear error); resource limits; trivy image shows no unaccepted critical findings.

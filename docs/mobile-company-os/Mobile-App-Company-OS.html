3Phase 1 - Market research & validationGate 1

OwnerBusiness Researcher (PM backup)
InputsIdea one-pager; industry & customer hypotheses
OutputMarket Research Report (PDF)
Exit gateGate 1

Procedure

  1. Write the problem statement in one sentence and name the buyer, user and payer.
  2. Collect competitor data from Google Play, Apple App Store, Product Hunt, G2/Capterra, Reddit, Google Trends and official sites. Log each fact in the evidence register below.
  3. Read the 1- and 2-star reviews of the top five competitors; tag complaints (missing feature, price, bug, support).
  4. Run ≥10 customer interviews (script: problem, current workaround, willingness to pay, budget owner).
  5. Size the market bottom-up: TAM = number of potential customers × annual revenue per customer; SAM = reachable segment; SOM = realistic 3-year capture. Cite the source of every count.
  6. Choose the monetisation model: paid, subscription, freemium or enterprise; justify with competitor pricing and interview evidence.
  7. Rate customer-acquisition difficulty (channels, cost, sales cycle) and state a go / pivot / stop recommendation.

Evidence register (mandatory format)

IDFindingSource URLAccess dateConfidence (H/M/L)Used for
E-001(example row) Competitor X lists price ₹___/monthhttps://…YYYY-MM-DDH - official pagePricing benchmark
E-002(example row) 38 of 120 reviews mention no offline modehttps://… (store page)YYYY-MM-DDM - own taggingFeature gap

Bottom-up sizing formula

TAM = N(potential customers) × ARPA(₹/yr)
SAM = TAM × share reachable via our channels and language/geography
SOM = SAM × realistic 3-yr share (state the basis; ≤5% unless evidence says otherwise)
No invented statistics
If a number cannot be sourced, write Unknown - research needed. Reports with unsourced figures are rejected at Gate 1. Use government sources (e.g. MeitY, ministry reports) and official competitor pages as primary evidence.

Procedure

  1. Write the PRD: objective, users, roles and permissions, modules, navigation, journeys, offline/online scope, integrations, SDKs, security, performance, device support, accessibility, maintenance.

Required architecture documents

  • Application architecture (C4 context + container)
  • Frontend architecture (layers, state, navigation)
  • Backend architecture (modules, queues)
  • Database architecture (ER diagram, indexes, migrations)
  • API architecture (REST, versioning, error model)
  • Authentication (OTP/password, JWT + refresh, device binding)
  • Notification architecture
  • Offline sync architecture (outbox, conflict policy)
  • File storage (signed URLs, lifecycle)
  • Threat model (STRIDE; MASVS mapping)
  • Cloud infrastructure diagram
Offline is a design decision
Define per entity: allowed offline operations, local retention, sync order, and conflict rule (e.g. server-wins for master data; append-only for reports; last-writer-wins only with timestamp + device id, and user-visible conflict screen for edits). Do not sync everything by default.

GitHub standards

  • Private repository per product; org-level 2FA enforced
  • main protected: PR required, ≥1 review, status checks required, no force-push
  • Branches: feature/-, fix/…, release/x.y.z; squash-merge
  • Commits: Conventional Commits (feat:, fix:, docs:, chore:) + task id
  • Actions: lint, unit tests, build APK/AAB/IPA debug, dependency & secret scan, CodeQL
  • Dependabot enabled; release tags vX.Y.Z; CHANGELOG generated
  • Environments dev / staging / production with separate secrets, databases and API URLs
  • Secrets only in GitHub/Cloud secret stores; .env.example lists names only
  • Pre-commit secret scan; signing keys stored offline + in vault, never in repo

A. Mobile frontend scope

  • Splash, onboarding, registration, login, forgot password
  • Dashboard, navigation, core modules per PRD
  • Forms, search/filter, reports
  • Notifications, profile, settings, help, logout

B. Backend scope

  • AuthN/AuthZ (RBAC), user management, business logic, REST endpoints + OpenAPI
  • Database access via migrations only; audit trail on writes
  • File management (signed URLs), notification service, payments if required
  • Structured logging with request ids; central error model

C. Offline standard

AspectStandard
Local DBSQLite via Drift; schema versioned and migrated
OutboxEvery offline write = row in outbox (id, entity, op, payload, created_at, attempts)
RetryExponential backoff + jitter, max attempts, then 'needs attention' list
ConflictRule per entity (see §5 callout); conflicts logged and surfaced
IndicatorsOffline banner, per-item 'pending' badge, 'last synced' timestamp
IdempotencyClient-generated UUID + Idempotency-Key header so retries never duplicate

D. Push notifications

  • Ask permission in context (not at first launch); explain value
  • Store device tokens per user-device; delete on logout; refresh on rotation
  • Handle invalid-token errors by pruning; never rely on push as the only channel
  • Per-category preferences and quiet hours; no personal data in payloads

E. Admin dashboard (if PRD requires)

  • User management, roles, settings
  • Analytics and reports
  • Subscription management, notifications, support tools
  • Audit-log viewer; every action by role-based access

Common rejections

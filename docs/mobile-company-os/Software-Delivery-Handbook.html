In plain words: software companyIt is a factory for software. Instead of machines it has process: the same steps for every project, so quality does not depend on luck.

A.2 Who is who

Team / roleWhat they do in simple wordsYou ask them when…
Founder / Managing DirectorDecides what the company builds and signs the big approvalsA gate needs final approval, or money is involved
CTO / Tech LeadChooses technology, protects code quality, reviews difficult codeYou are unsure how to build something
Product Manager (PM)Talks to customers, writes requirements, controls scope, schedule and budgetYou are unsure what to build or something changes
UI/UX DesignerDesigns how the app looks and how people use itA screen is unclear or does not fit
Mobile DeveloperBuilds the app people install on phonesApp screens, device problems

Database / DevOps EngineerKeeps databases, servers, deployments and backups runningDeployments, environments, secrets
QA Engineer (tester)Tries to break the app before customers do; decides if it can be releasedTest cases, bug severity
Sales / SupportDemos, contracts, customer questions after deliveryCustomer complaints and requests

In a small team one person may wear several hats. The jobs still exist - ask which hat someone is wearing when they give you an instruction.

In plain words: ticketA small written task with a number, an owner, a deadline and a clear 'done' definition, stored in the project tracker. All work starts from a ticket.

A.7 Company rules you must follow from day one

RuleWhy
Never put passwords, keys or customer data in code, chat or screenshotsUse the secret manager; keys leak through Git history forever
Use two-factor authentication on email, GitHub and cloud accountsStolen password alone must not be enough
Work only on company-approved tools and storageClient code on a personal drive is a legal and security problem
One task = one branch = one pull requestSmall changes are easy to review and to undo
Nobody merges their own code without a reviewA second pair of eyes catches mistakes
Never test with real customer dataUse synthetic (fake) data
Write it downIf it is not in the ticket, document or message, it did not happen

A.8 When you are stuck - the stuck ladder

  1. Try for 30 minutes: read the error message completely, search it, check the docs.
  2. Write the problem in 3 lines: what you wanted, what happened, what you tried.
  3. Ask a teammate with that note.
  4. Still stuck after another 30 minutes: ask the lead. Mark the ticket Blocked.
  5. Production problem or customer data risk: tell the lead immediately, do not wait.
Professional habits that get noticed
Update tickets before asked · reply to messages within working hours · say 'I do not know yet, I will find out by 3 pm' instead of staying silent · estimate honestly · admit mistakes early.

A.9 What a Gate is

In plain words: gateA checkpoint between two stages. A manager checks your evidence and signs. No signature = you do not start the next stage. This protects the customer's money and your time.

B.3 Folder system inside the code repository

sitediary/                          <- the Git repository (what developers share)
  README.md             <- what this project is + how to run it (read first!)
  CONTRIBUTING.md       <- team rules: branches, commits, reviews
  .gitignore            <- list of files Git must never store (secrets, build output)
  .env.example          <- NAMES of settings (no real passwords)
  .github/workflows/    <- automatic checks that run on every pull request
  mobile/               <- the phone app (Flutter)
    lib/
      core/             <- shared helpers: errors, constants, utilities
      config/           <- environment settings (dev / staging / prod URLs)
      services/         <- talks to outside things: API, storage, notifications
      models/           <- data shapes (Site, Report, Worker)
      repositories/     <- one place to read/write each kind of data (API or local DB)
      features/         <- one folder per feature: auth/, sites/, reports/, sync/
      widgets/          <- reusable UI pieces (buttons, cards)
      navigation/       <- screens and routes
      state/            <- app state management
    assets/             <- images, icons, fonts
    test/               <- automatic tests for logic and widgets
    integration_test/   <- tests that click through whole flows
  backend/              <- the server (NestJS)
    src/                <- server code, one folder per module (auth, sites, reports, files)
    tests/              <- server tests
    migrations/         <- database change scripts, numbered, never edited after merge
  admin-dashboard/      <- web admin (only if the requirements need it)
  docs/                 <- project knowledge that travels with the code
    requirements/ architecture/ api/ database/ ui-ux/ deployment/ testing/
  infra/                <- server and deployment configuration files
In plain words: repository (repo)The project's code folder with its full history, stored on GitHub. Everyone gets a copy (clone), makes changes on a branch, and merges them back through a pull request.
Never do thisDo not store source code only on your laptop or in a zip file by email. If it is not in Git, it does not exist.

Time guide1 - 2 days

In plain words: stage 0Nothing is built here. You are only making sure you can work safely and others can find your work.

Steps

1

Get your accounts

Company email · GitHub (join the organisation) · project tracker · design tool · cloud console (view access only at first) · password manager. Turn on two-factor authentication on every one.

2

Prepare your laptop

Install: Git, VS Code, Node.js (LTS), Flutter SDK, Android Studio. macOS only for iOS: Xcode. Check each with the commands below.

git --version
node -v
flutter --version
flutter doctor -v
Tipflutter doctor shows a ✗ next to anything missing. Fix them one by one using its instructions.
3

Set your Git identity

git config --global user.name "Your Name"
git config --global user.email "you@company.com"
git config --global init.defaultBranch main
4

Create your SSH key and add it to GitHub

This is your secure ID card for GitHub.

ssh-keygen -t ed25519 -C "you@company.com"
cat ~/.ssh/id_ed25519.pub

Copy the printed line into GitHub → Settings → SSH and GPG keys → New SSH key. Never share the file without .pub.

5

Create your folder system

Use the commands in section B.1. Put the project folder in the company drive.

6

Read the project documents

README.md, CONTRIBUTING.md and the requirements (PRD) of the project you join. Write 5 questions you still have and ask them in the first 1-to-1.

7

Do the 'hello' test

Clone the repo, run the app on an emulator or phone, change one text, make a branch, commit and open a pull request. This proves your setup works.

git clone git@github.com:<org>/<repo>.git
cd <repo>/mobile
flutter pub get
flutter run
What you must hand in (output)Screenshot of flutter doctor with no ✗ for your targets · your first merged pull request · folder structure created · accounts list ticked

Quality check

  • 2FA on all accounts
  • flutter doctor clean for chosen targets
  • SSH key works (ssh -T git@github.com)
  • Folder structure created exactly as B.1
  • I know who my lead and mentor are

Common mistakes

  • Skipping 2FA 'for now'
  • Installing tools from random websites - use official downloads only
  • Saving code in Downloads or Desktop

1. Business check

01
PLAN · STAGE 1 OF 13
Business check
Is this worth building? Find out before spending money
Time guide1 - 2 weeks
You work withPM, Founder, 10+ real people
ToolsGoogle Play, App Store, Google Trends, Reddit, G2/Capterra, spreadsheet
Approved byFounder (Gate 1)
In plain words: why research firstThe most expensive mistake is building something nobody pays for. A week of research can save months of work.

Steps

1

Write the idea in one sentence

PROBLEM STATEMENT
Who has the problem?Site supervisors in small construction firms
What is the problem?Daily site records are lost or late because of poor network and paper
How do they solve it today?Paper notebooks, WhatsApp photos
What would success look like?Owner receives a complete report every evening
2

Find existing apps

Search Google Play and the App Store with 5 different keywords. Open the 5 best apps. Write: name, price, rating, number of reviews, last update date, main features.

3

Read the complaints

Open each app's 1-star and 2-star reviews. Tag each complaint: missing feature · price · bug · support. Count them. The most common tag is your opportunity.

4

Talk to 10 real customers

  1. Ask for 30 minutes. Do not sell. Ask how they work today.
  2. Questions: What was the last time this problem happened? What did it cost? What do you use now? What would you pay?
  3. Write notes the same day. Ask for a 60-day pilot or a small deposit at the end.
5

Write every fact in the Evidence Register

IDFactSource URLDate accessedConfidence
E-001Competitor X charges ₹___/monthhttps://…2026-11-05High (official page)
Never do thisNever write a number without a source. If you cannot find it, write Unknown - research needed.
6

Estimate market size bottom-up

TAM = number of possible customers × yearly revenue per customer
SAM = the part you can reach in your language/region/channel
SOM = the part you can realistically win in 3 years

Use sourced counts (e.g. government or industry numbers). Show your arithmetic.

7

Decide how it makes money

ModelUse when
SubscriptionCustomers get value every month (recommended default)
One-time paid appSingle-use tool
FreemiumFree users cost almost nothing to serve
Enterprise contractLarge buyers, custom needs
8

Score the idea and recommend

Use the scorecard in the OS document (§3): ≥70 Go · 50-69 Pivot · <50 Stop. Write one page: recommendation and why.

9

Present and get Gate 1

Send the report to the Founder. Gate 1 is approved only with evidence and interview proof.

What you must hand in (output)Market Research Report (PDF) · Evidence Register (sheet) · interview notes · go/pivot/stop scorecard

Quality check

  • Every number has URL + date + confidence
  • ≥ 10 interviews done and noted
  • ≥ 5 competitors compared
  • Bottom-up sizing shows its formula
  • Recommendation is clear

Common mistakes

  • Asking friends who are not customers
  • Copying statistics from random blogs
  • Falling in love with the idea and ignoring the score

2. Requirements

02
PLAN · STAGE 2 OF 13
Requirements
Write exactly what will be built - and freeze it
Time guide1 - 2 weeks
You work withPM, designer, tech lead, QA
ToolsDocument editor, tracker, spreadsheet
Approved byFounder + customer (Gate 2)
In plain words: scope freezeAgreeing in writing what is included. It protects the customer from surprise bills and the team from endless changes.

Steps

1

List users and roles

Who uses the app? (Owner, Manager, Supervisor, Worker). What may each role do? Draw a table: capability × role (see OS §4).

2

List the modules (big features)

Example: Login · Sites · Daily report · Photos · Offline sync · Notifications · Admin. Mark each Must / Should / Could / Won't (MoSCoW). The first release is only the Musts.

3

Draw the screen list

Give every screen an ID: S-001 Login, S-010 Site list, S-014 Attendance … This ID is used in tickets, tests and code.

4

Fill one Screen Sheet per screen

SCREEN SHEET - S-014 Attendance
Purpose / roleRecord who worked today / Supervisor
Inputsworker (pick list, required) · status (present/absent/half) · hours (0-16, step 0.5) · note (≤200 characters)
Validationhours required if present; no duplicate worker per day
ButtonsSave → store on phone + send later · Submit → lock the day
Calls APIPOST /v1/reports/{id}/attendance
DatabaseUPSERT attendance
ErrorsE-4101 'Hours must be between 0 and 16'
Loading / offlineSkeleton rows · works fully offline · 'Pending sync' badge
5

Write what happens when things fail

SituationApp must…
No internetKeep working; save locally; show 'Offline'
Slow internetShow saved data first; retry; never lose typed data
Server errorFriendly message + Retry
Session expiredSave draft, ask login, restore draft
Wrong passwordGeneric message; lock after 5 tries
Phone restartedReopen on same screen with draft
6

Review with everyone

Designer checks screens, tech lead checks feasibility, QA checks that every rule can be tested. Fix all open questions.

7

Freeze the scope

Tag the document PRD v1.0 - FROZEN. From now on any new idea needs a Change Request.

CHANGE REQUEST
CR number / dateCR-001 / ____
Requested by____
What and why____
Hours and cost (use rate card)____
Delay (days)____
Decision☐ Approve ☐ Reject ☐ Later - signed ____
What you must hand in (output)PRD v1.0 (frozen) · all Screen Sheets · screen→API→database table · failure behaviour table · signed Gate 2

Quality check

  • Every screen has an ID and a sheet
  • Every input has type, validation, required/optional
  • Offline rules written per feature
  • Roles and permissions table complete
  • Customer or Founder signed

Common mistakes

  • 'The developer will figure it out' - write it
  • Adding features during build without a change request
  • Forgetting error and empty screens

3. Technology & architecture

03
DESIGN & SETUP · STAGE 3 OF 13
Technology & architecture
Choose the tools and draw the blueprint before building
Time guide3 - 5 days
You work withTech lead, PM
ToolsDiagram tool, document editor
Approved byCTO (Gate 3)
In plain words: architectureThe blueprint of the system: what parts exist, how they connect, and how data flows - like drawings before constructing a building.

Steps

1

Re-read the frozen requirements

List what really drives the technology: offline needed? photos? payments? how many users? which countries?

2

Ask: do we even need a mobile app?

If a responsive website or PWA can do the job, recommend it. Mobile apps cost more to build, publish and maintain.

3

Compare the options with the scoring table

Score each option 1-5 per criterion, multiply by weights, add up (example in OS §5). Highest score wins unless the team cannot support it.

In plain words: Flutter / nativeNative = separate Android (Kotlin) and iOS (Swift) apps - best device access, double cost. Flutter = one codebase for both - faster and cheaper, most features available.
4

Draw the system diagram

  [ Phone app (Flutter) ] --HTTPS--> [ API server (NestJS) ] --> [ PostgreSQL database ]
     |   local SQLite DB             |        |  \--> [ File storage: photos, PDFs ]
     |   (offline data + outbox)     |        \----> [ Push service: FCM ]
     \--> works offline, syncs later  \--> [ Logs + monitoring ]
  [ Admin web dashboard ] --HTTPS--> same API server

Each box is one thing you must build, host or buy. Each arrow is a connection that must be secure.

5

Design the data (ER diagram)

List the things the system remembers (Organisation, User, Site, Worker, Report, Attendance, Photo) and how they connect (a Site has many Reports; a Report has many Attendance rows). Draw boxes and lines.

6

List the API endpoints

Method + pathPurpose
POST /v1/auth/otp/verifyLog in
GET /v1/sitesList sites
POST /v1/reports/{id}/attendanceSave attendance
POST /v1/uploadsUpload photo
POST /v1/reports/{id}/submitSubmit day
In plain words: APIA menu of requests the server understands. The phone asks, the server answers with data.
7

Decide login and offline rules

Login method (OTP/password), how long sessions last, which data may be changed offline, and what happens when two devices change the same thing (conflict rule). Write each rule in one sentence.

8

Do a basic security think-through

  • What data is sensitive?
  • Where is it stored on the phone? (secure storage for tokens)
  • Who can see whose data? (every request is checked on the server)
  • What if the phone is lost?
  • Which outside SDKs will we add, and what do they collect?
9

Write the Decision Record and get Gate 3

ADR-001 - Framework decision
ContextOffline required, 6-person team, Android + iOS
OptionsFlutter, Native, React Native, PWA
DecisionFlutter + NestJS + PostgreSQL
BecauseScore table, team skills, cost
Risks / revisit whenHeavy device features needed later
Approved by / dateCTO ____
What you must hand in (output)Decision Record (ADR) · system diagram · ER diagram · API endpoint list · login/offline/security notes · Gate 3

Quality check

  • Options compared with scores
  • Web/PWA alternative considered
  • Diagram shows every component and connection
  • Data model reviewed by backend and mobile developers
  • Security questions answered

Common mistakes

  • Choosing a tool because it is popular
  • No offline rule, then surprise duplicate data
  • Skipping the diagram and 'keeping it in head'

4. UI / UX design

04
DESIGN & SETUP · STAGE 4 OF 13
UI / UX design
Decide how the app looks and feels - and test it with real users
Time guide2 - 4 weeks
You work withDesigner, PM, 5 test users
ToolsFigma (or similar), prototype link
Approved byPM + customer (Gate 4)
In plain words: UI vs UXUI = how it looks (colours, buttons). UX = how easy it is to use (steps, clarity).

Steps

1

Map the user journeys

For each role draw the path from opening the app to finishing the main task. Mark where things can go wrong.

2

Draw the screen list and navigation

Use the same screen IDs as the requirements. Decide bottom tabs, menus and back behaviour.

3

Sketch low-fidelity wireframes

Black-and-white boxes only. Focus on what is on the screen and where, not colours. Review with the PM.

4

Create the design system (tokens)

TokenExample
ColoursPrimary #0B5FFF, Success #0F7B45, Error #B3261E, Text #17202A
Type scaleTitle 22, Body 16, Caption 12
Spacing4 / 8 / 16 / 24 px
Radius8 px cards, 24 px buttons
TipDefine once, reuse everywhere. Never type a colour by hand in a screen.
5

Design the high-fidelity screens

Use Material guidance for Android and Human Interface guidance for iOS. Touch targets at least 48 dp (Android) / 44 pt (iOS). Text contrast at least 4.5:1.

6

Design every state

StateShow
LoadingSkeleton or spinner
EmptyExplain + one action button
ErrorWhat happened + Retry
OfflineBanner + 'pending' badge
PermissionWhy camera/location is needed before the system popup
7

Make a clickable prototype

Link the screens for the 5 main journeys. A non-designer should be able to click through without help.

8

Test with 5 real users

Give a task ('Record today's attendance'). Watch silently. Note where they hesitate. Calculate task success rate. Fix major problems.

9

Hand off to developers

Share the Figma link, exported icons, tokens, and notes. Walk the developers through the prototype in a 30-minute meeting.

What you must hand in (output)Figma file link · clickable prototype · design tokens · component list · usability test notes · Gate 4

Quality check

  • Every PRD screen is designed in every state
  • Accessibility checked (contrast, size, labels)
  • 5 users tested; ≥80% task success
  • Original design - nothing copied from competitors
  • Developers acknowledged the hand-off

Common mistakes

  • Designing only the happy path
  • Tiny text and buttons
  • Hand-off by chat message instead of a walkthrough

4

Write the endpoint with validation

// backend/src/reports/dto/create-attendance.dto.ts
import { IsIn, IsNumber, IsOptional, IsString, IsUUID, Max, MaxLength, Min } from 'class-validator';
export class CreateAttendanceDto {
  @IsUUID() workerId: string;
  @IsIn(['present', 'absent', 'half']) status: string;
  @IsOptional() @IsNumber() @Min(0) @Max(16) hours?: number;
  @IsOptional() @IsString() @MaxLength(200) note?: string;
}
// backend/src/reports/reports.controller.ts
@Controller('v1/reports')
export class ReportsController {
  constructor(private readonly service: ReportsService) {}

  @Post(':id/attendance')
  addAttendance(@Param('id') id: string, @Body() dto: CreateAttendanceDto) {
    return this.service.addAttendance(id, dto);   // business logic lives in the service
  }
}
// main.ts: app.useGlobalPipes(new ValidationPipe({ whitelist: true }));

Controller = receives request. DTO = checks the input. Service = business logic. Repository = database access. Keep them separate.
